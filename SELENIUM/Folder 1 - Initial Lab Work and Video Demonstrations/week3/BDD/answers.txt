1. WHAT ARE THE BDD TOOLS WE USE TO AUTOMATE IN PYTHON LANGUAGE
--------------------------------------------------------------------------------
Behavior-Driven Development (BDD) is a software development methodology that encourages 
collaboration among developers, QAs, and business stakeholders. Tests are specified in 
Gherkin syntax (`Given-When-Then`).

Python BDD Tools Ecosystem:

1. `behave` (Recommended & Industry Standard):
   - Python's official implementation of the Cucumber Gherkin standard.
   - Native support for feature files, scenario outlines, step parameters, environment hooks, 
     and tagging.
   - Clean integration with `requests`, `selenium`, and `allure-behave`.

2. `pytest-bdd`:
   - Plugin that combines BDD specification with the powerful `pytest` test runner.
   - Leverages native `pytest` fixtures, parameterization, and plugins.

3. `radish` / `lettuce`:
   - Legacy Python BDD frameworks (largely unmaintained).

2. CREATE STEP DEFINITION FILE WITH AUTO GENERATED SYNTAXES AND ANNOTATIONS
--------------------------------------------------------------------------------
When running `behave` with undefined steps in a `.feature` file, the `behave` test runner 
automatically generates step definition code snippets in the terminal console.

A. Auto-Generated Snippet Output Example:
```text
You can implement step definitions for the new steps using these snippets:

@when(u'I send a POST request to "{endpoint}" with title "{title}"')
def step_impl(context, endpoint, title):
    raise NotImplementedError(u'STEP: When I send a POST request to...')
```

B. Step Annotations (`@given`, `@when`, `@then`, `@step`):
- `@given`: Specifies pre-requisite initial state (e.g., setting base URL or auth token).
- `@when`: Specifies action or event being tested (e.g., executing HTTP API call).
- `@then`: Specifies expected outcome or assertion check (e.g., checking status code).
- `@step`: Generic step decorator usable for any keyword.

C. Parameter Matchers:
1. Standard Parse Matcher:
   ```python
   @when('I send a GET request to "{endpoint}"')
   def step_get(context, endpoint):
       context.response = requests.get(context.base_url + endpoint)
   ```

2. Regex Matcher:
   ```python
   from behave import step, use_step_matcher
   use_step_matcher("re")

   @step(r'the status code should be (?P<code me>\d+)')
   def step_status_regex(context, code):
       assert context.response.status_code == int(code)
   ```

3. IMPLEMENT API AUTOMATION ACTUAL LOGIC INTO STEP DEFINITIONS
--------------------------------------------------------------------------------
Actual API logic (using `requests`) is embedded within the step functions, sharing data 
across steps using the `context` object.

Step Definition Implementation (`steps/api_steps.py`):
```python
from behave import given, when, then
import requests

@given('the API base URL is "{base_url}"')
def set_base_url(context, base_url):
    context.base_url = base_url
    context.session = requests.Session()

@when('I create a user with name "{name}" and job "{job}"')
def create_user(context, name, job):
    payload = {"name": name, "job": job}
    url = f"{context.base_url}/api/users"
    context.response = context.session.post(url, json=payload)

@then('the response status code should be {status_code:d}')
def verify_status_code(context, status_code):
    assert context.response.status_code == status_code, \
        f"Expected {status_code}, got {context.response.status_code}"

@then('the response body should contain key "{key_name}"')
def verify_json_key(context, key_name):
    json_data = context.response.json()
    assert key_name in json_data, f"Key '{key_name}' missing in response!"
```

4. IMPLEMENT HOOKS FOR SCENARIOS BY DEFINING ENVIRONMENT.PY FILE
--------------------------------------------------------------------------------
The `environment.py` file placed inside the `features/` directory defines global 
lifecycle hook functions executed automatically by `behave`.

Available Hook Functions:
- `before_all(context)` / `after_all(context)`: Executed once before/after entire test suite.
- `before_feature(context, feature)` / `after_feature(context, feature)`: Executed per feature.
- `before_scenario(context, scenario)` / `after_scenario(context, scenario)`: Executed per scenario.
- `before_step(context, step)` / `after_step(context, step)`: Executed before/after each step.
- `before_tag(context, tag)` / `after_tag(context, tag)`: Executed when encountering a specific tag.

Sample `environment.py` Implementation:
```python
import requests
import logging

def before_all(context):
    print("\n[HOOK] Initializing Global Test Environment...")
    context.global_config = {
        "base_url": "https://reqres.in",
        "timeout": 10
    }
    logging.basicConfig(level=logging.INFO)

def before_scenario(context, scenario):
    print(f"\n[HOOK] Starting Scenario: '{scenario.name}'")
    context.session = requests.Session()
    context.session.headers.update({"Accept": "application/json"})

def after_scenario(context, scenario):
    print(f"[HOOK] Cleaning up after Scenario: '{scenario.name}' (Status: {scenario.status})")
    if hasattr(context, "session"):
        context.session.close()

def after_all(context):
    print("\n[HOOK] All Scenarios completed. Tearing down environment.")
```

6. USE TAGGING MECHANISM TO RUN SELECTED TESTS IN FRAMEWORK
--------------------------------------------------------------------------------
Tags (`@tag_name`) categorize scenarios and features for selective test execution.

A. Tagging Gherkin Scenarios:
```gherkin
@api @smoke
Feature: Core API Smoke Tests

  @login @critical
  Scenario: Valid user login
    Given the login endpoint is ready
    When I post valid credentials
    Then status code is 200

  @regression @wip
  Scenario: Password reset workflow
    Given the reset endpoint is ready
    When I request password reset
    Then confirmation email is dispatched
```

B. Executing Tagged Tests via CLI:
```bash
# Run only @smoke scenarios
behave --tags=@smoke

# Run scenarios with BOTH @api AND @smoke
behave --tags="@api and @smoke"

# Run scenarios with @smoke OR @regression
behave --tags="@smoke or @regression"

# Skip work-in-progress (@wip) scenarios
behave --tags="not @wip"
```

7. BEST PRACTICES TO WRITE REUSABLE STEP DEFINITIONS CODE FOR API TEST SCENARIOS
--------------------------------------------------------------------------------
1. Keep Steps Declarative (Business Focus) rather than Imperative (Low-level Implementation details).
2. Use Parameter Types in step matchers (`{status_code:d}` for integers, `{endpoint:s}` for strings).
3. Do not couple steps tightly; pass dynamic state using `context`.
4. Avoid duplicate step matchers across step definition files.
5. Abstract API client calls into separate reusable Helper/Service classes outside step definition files.

9. GENERATE ALLURE REPORTS FOR PYTHON API BDD FRAMEWORK
--------------------------------------------------------------------------------
Allure Report is a flexible, lightweight multi-language test report tool with rich graphs 
and detailed test step visualizers.

A. Installation:
```bash
pip install allure-behave
```

B. Attaching API Payloads & Status Codes in Steps:
```python
import allure

@then('the response status code should be {status_code:d}')
def verify_status_allure(context, status_code):
    allure.attach(
        body=str(context.response.status_code),
        name="Actual HTTP Status Code",
        attachment_type=allure.attachment_type.TEXT
    )
    allure.attach(
        body=context.response.text,
        name="Response Body JSON",
        attachment_type=allure.attachment_type.JSON
    )
    assert context.response.status_code == status_code
```

C. Running Tests and Generating Allure Report:
```bash
# Step 1: Run behave tests and output allure results to folder
behave -f allure_behave.formatter:AllureFormatter -o reports/allure-results

# Step 2: Generate visual HTML report using Allure CLI
allure generate reports/allure-results -o reports/allure-report --clean

# Step 3: Open visual report in web browser
allure open reports/allure-report
```

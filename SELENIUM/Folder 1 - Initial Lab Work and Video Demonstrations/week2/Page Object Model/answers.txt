--------------------------------------------------------------------------------
1. WHY TO HAVE FRAMEWORK
--------------------------------------------------------------------------------
In test automation, writing monolithic scripts where locators, test steps, test data, 
and driver initialization are all combined in a single file leads to major problems:

Disadvantages of Unstructured Automation Scripts:
1. High Code Duplication: Locators and user interaction steps are duplicated across 
   multiple test scripts.
2. High Maintenance Effort: If a UI locator or element property changes, you must 
   update every single script that references that locator.
3. Hardcoded Test Data: Hardcoded credentials and URLs make tests rigid and non-reusable.
4. Poor Readability & Scalability: Non-technical stakeholders cannot understand test logic.

Benefits of a Test Automation Framework:
1. Reusability: Common wrapper methods, page objects, and utilities are written once 
   and reused everywhere.
2. Maintainability: UI element locators are stored in designated Page classes. If UI 
   changes, updates are made in one place only.
3. Separation of Concerns: Test logic is decoupled from UI locator strategy and test data.
4. Parallel Execution & Reporting: Built-in support for test runners, logging, HTML reports, 
   and CI/CD integration.


--------------------------------------------------------------------------------
2. UNDERSTANDING OF BASE CLASS, PAGE CLASS, TEST CLASS, UTILITIES CLASSES, CONFIGURATION FILE AND SCREENSHOTS
--------------------------------------------------------------------------------
A standard Page Object Model architecture comprises the following key components:

1. Base Class (`BasePage`):
   - Contains wrapper functions around native Selenium WebDriver methods (e.g., custom 
     click, type/send_keys, wait for element visibility, scroll, get text).
   - Keeps WebDriver initialization clean and ensures explicit wait mechanisms are applied 
     consistently across all page interactions.

2. Page Class:
   - Represents a specific Web Page or Component (e.g., `LoginPage`, `DashboardPage`).
   - Encapsulates:
     a) Locators (By.ID, By.XPATH, etc.) for elements on that page.
     b) Action Methods representing user operations on that page (e.g., `enter_username()`, 
        `click_login_button()`).

3. Test Class (`test_*.py`):
   - Contains actual test cases and assertion statements.
   - Instantiates Page classes, calls page action methods, and asserts expected results.
   - Contains NO direct `driver.find_element` or raw XPath references.

4. Utilities Classes (`utils/`):
   - Helper scripts for auxiliary capabilities:
     - Data Readers (reading CSV, Excel, JSON, YAML).
     - Logger setup (Python `logging` module).
     - Database or API helpers.

5. Configuration File (`config.ini` / `config.properties` / `.env`):
   - Central location for global environment variables (Base URL, browser choice, 
     default timeouts, user credentials).

6. Screenshots Directory (`screenshots/`):
   - Captures and stores visual images (.png) of web pages automatically when test 
     failures occur during test execution.


--------------------------------------------------------------------------------
3. WHAT IS PAGE OBJECT MODEL (POM)
--------------------------------------------------------------------------------
Page Object Model (POM) is an industry-standard design pattern in test automation 
that creates an Object Repository for web UI elements.

Under POM:
- Every web page in the application under test is treated as a corresponding Page Class.
- Web elements on the page are defined as variables/locators within the class.
- Operations performed on the web page are defined as public methods within the class.

Key Principle of POM:
Test scripts should never directly interact with the DOM or WebDriver locators. Instead, 
they delegate element interactions to Page Objects.

Architectural Overview:

  +-----------------------+           +-----------------------+
  |    Test Script        |           |      Page Class       |
  |  (test_login.py)      | --------> |     (LoginPage.py)    |
  |  - Calls page methods |           |  - Holds Locators     |
  |  - Asserts outcomes   |           |  - Defines Actions    |
  +-----------------------+           +-----------------------+
                                                  |
                                                  v
                                      +-----------------------+
                                      |      Base Class       |
                                      |     (BasePage.py)     |
                                      |  - Custom WebWaits    |
                                      |  - Driver Wrappers    |
                                      +-----------------------+

4. BASEPAGE AND UTIL CONCEPT
--------------------------------------------------------------------------------
BasePage Concept:
The `BasePage` serves as the parent class for all Page Classes. It accepts the `driver` 
instance in its `__init__` constructor and encapsulates robust element interactions 
with explicit waits (`WebDriverWait`).

Example `BasePage.py`:

```python
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

class BasePage:
    def __init__(self, driver, timeout=10):
        self.driver = driver
        self.wait = WebDriverWait(driver, timeout)

    def do_click(self, locator):
        """Wait for element to be clickable, then click."""
        element = self.wait.until(EC.element_to_be_clickable(locator))
        element.click()

    def do_send_keys(self, locator, text):
        """Wait for element visibility, clear field, and enter text."""
        element = self.wait.until(EC.visibility_of_element_located(locator))
        element.clear()
        element.send_keys(text)

    def get_element_text(self, locator):
        """Wait for element visibility and return text."""
        element = self.wait.until(EC.visibility_of_element_located(locator))
        return element.text

    def is_visible(self, locator):
        """Check if element is visible on page."""
        element = self.wait.until(EC.visibility_of_element_located(locator))
        return bool(element)
```


--------------------------------------------------------------------------------
5. INHERITING BASEPAGE CLASS
--------------------------------------------------------------------------------
Every Page Object Class inherits from `BasePage` to gain access to reusable web 
interaction wrappers (`do_click`, `do_send_keys`, etc.).

Example Page Class Inheriting `BasePage`:

```python
from selenium.webdriver.common.by import By
# Assuming BasePage is imported from base_pages.BasePage
from base_pages.BasePage import BasePage

class LoginPage(BasePage):
    # Locators Encapsulation
    USERNAME_INPUT = (By.ID, "Email")
    PASSWORD_INPUT = (By.ID, "Password")
    LOGIN_BUTTON   = (By.XPATH, "//button[@type='submit']")
    ERROR_MSG      = (By.CLASS_NAME, "message-error")

    def __init__(self, driver):
        # Call parent constructor
        super().__init__(driver)

    # Action Methods
    def enter_username(self, username):
        self.do_send_keys(self.USERNAME_INPUT, username)

    def enter_password(self, password):
        self.do_send_keys(self.PASSWORD_INPUT, password)

    def click_login(self):
        self.do_click(self.LOGIN_BUTTON)

    def login_to_application(self, username, password):
        self.enter_username(username)
        self.enter_password(password)
        self.click_login()

    def get_error_message(self):
        return self.get_element_text(self.ERROR_MSG)
```

6. UTILITY TO READ CSV DATA
--------------------------------------------------------------------------------
Reading external data from CSV files enables Data-Driven Testing (DDT).

Example CSV Data Reader Utility (`excel_util.py` or `csv_reader.py`):

```python
import csv

def read_csv_data(file_path):
    """Reads CSV file and returns list of data rows (excluding header)."""
    data_list = []
    with open(file_path, mode='r', newline='', encoding='utf-8') as file:
        reader = csv.reader(file)
        next(reader)  # Skip header row
        for row in reader:
            data_list.append(row)
    return data_list
```

Integrating CSV Utility with PyTest Parameterize:

```python
import pytest
from utilities.csv_reader import read_csv_data

# Read test data from CSV file
test_data = read_csv_data("test_data/login_credentials.csv")

@pytest.mark.parametrize("username, password, expected_status", test_data)
def test_login_from_csv(driver, username, password, expected_status):
    login_page = LoginPage(driver)
    login_page.login_to_application(username, password)
    # Perform assertions based on expected_status
```

7. CONVERT TEST CASE TO PAGE OBJECT MODEL FRAMEWORK
--------------------------------------------------------------------------------
Comparison of non-POM script vs POM Refactored script:

BEFORE (Monolithic Unstructured Script):
```python
def test_admin_login():
    driver = webdriver.Chrome()
    driver.get("https://admin-demo.nopcommerce.com/login")
    
    email_field = driver.find_element(By.ID, "Email")
    email_field.clear()
    email_field.send_keys("admin@yourstore.com")
    
    pass_field = driver.find_element(By.ID, "Password")
    pass_field.clear()
    pass_field.send_keys("admin")
    
    login_btn = driver.find_element(By.XPATH, "//button[@type='submit']")
    login_btn.click()
    
    assert driver.title == "Dashboard / nopCommerce administration"
    driver.quit()
```

AFTER (Clean POM Architecture):

1. `base_pages/LoginPage.py`:
```python
from base_pages.BasePage import BasePage
from selenium.webdriver.common.by import By

class LoginPage(BasePage):
    EMAIL_INPUT = (By.ID, "Email")
    PASSWORD_INPUT = (By.ID, "Password")
    LOGIN_BTN = (By.XPATH, "//button[@type='submit']")

    def __init__(self, driver):
        super().__init__(driver)

    def login(self, email, password):
        self.do_send_keys(self.EMAIL_INPUT, email)
        self.do_send_keys(self.PASSWORD_INPUT, password)
        self.do_click(self.LOGIN_BTN)
```

2. `test_cases/test_admin_login.py`:
```python
from base_pages.LoginPage import LoginPage

def test_admin_login(driver):
    driver.get("https://admin-demo.nopcommerce.com/login")
    login_page = LoginPage(driver)
    login_page.login("admin@yourstore.com", "admin")
    assert driver.title == "Dashboard / nopCommerce administration"
```

8. TAKING SCREENSHOTS ON TEST FAILURE
--------------------------------------------------------------------------------
Capturing screenshots automatically on test failure is essential for failure diagnosis 
in automated test runs.

Method 1: Manual Driver Screenshot Capture

```python
driver.save_screenshot("screenshots/failure_screenshot.png")
# or
driver.get_screenshot_as_file("screenshots/test_failure.png")
```

Method 2: Automatic PyTest Failure Hook in `conftest.py`

By implementing the `pytest_runtest_makereport` hook in `conftest.py`, PyTest can 
automatically capture a screenshot whenever a test fails and save it with a timestamp 
or attach it to PyTest-HTML reports.

Example `conftest.py` Hook:

```python
import pytest
import os
from datetime import datetime

@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    
    if report.when == 'call' and report.failed:
        driver = item.funcargs.get('driver')
        if driver:
            screenshots_dir = "screenshots"
            os.makedirs(screenshots_dir, exist_ok=True)
            timestamp = datetime.now().strftime("%Y-%m-%d_%H-%M-%S")
            file_name = f"{screenshots_dir}/{item.name}_{timestamp}.png"
            driver.save_screenshot(file_name)
            print(f"\n[SCREENSHOT CAPTURED] Saved to {file_name}")
```

Benefits:
- Runs automatically without needing manual screenshot logic in every test case.
- Pinpoints the exact visual state of the browser at the instant of test failure.
